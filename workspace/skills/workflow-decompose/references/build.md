# 建置：把藍圖變成可以做出來的東西

只在**藍圖已經確認**、而且使用者說要開始做（例如「幫我建起來」「接著做」）時才進入。藍圖還沒確認，先回模式 1。

**先判斷走哪條路線**（用一句話告訴使用者你判斷走哪條，請他確認；不確定就問）：
- **路線 A：排程整理資料。** 藍圖的資料來自網頁或公開資料、不需要記錄自己的資料，結果是定時產出一份整理。往下看「路線 A」。
- **路線 B：查詢與記錄自己資料的助理。** 藍圖要查或寫使用者自己的資料（例如庫存、訂單），用對話一句一句問、一句一句做。跳到「路線 B」。

---

## 路線 A：排程整理資料

你有「自動化」工具，可以在使用者同意後替他建立排程；你**不能**執行指令。這條路線做四件事：問缺的資料、起草任務指示、在這個對話裡先跑一次、問使用者要不要替他建立（一律建成停用）。**沒有呼叫自動化工具成功之前，不要說你已經建立了排程。**

## 步驟 1：補缺少的具體資料（一次一題）
藍圖通常只有「約五個公開網站」這種說法，沒有網址。缺什麼就問什麼，**不可以自己編網址、檔名或時間**：
- **第一題**：「請一次把你要用的所有資料來源（名稱與網址）貼給我。」讓使用者**一次全部給**，不要一個來源問一次。使用者說不知道網址，就請他提供，或說明建置要等有來源再繼續。使用者給的清單你照樣整理成「來源 1、來源 2…」回給他確認。
- 每天幾點執行（預設台北時間）。
- 這個自動化要叫什麼名稱（預設用 `daily-` 加主題，例如 `daily-news`）。

## 步驟 2：起草任務指示
用下面的骨架，內容**只用藍圖裡使用者確認過的話**，繁體中文，不超過約 1,500 字。**不要替使用者補性別、稱謂或年齡**（例如不要寫「她」「他」，用「承辦人」「使用者」）；藍圖沒說的人事時地物，一律不寫：
1. 一句角色說明（來自藍圖的定位）。
2. 「用 web_fetch 逐一讀這些來源，讀不到就如實記錄『讀取失敗』，不要用記憶補內容」，列出來源代號、名稱、網址。
3. 整理規則（來自藍圖的輸出與資料）：怎麼分類、怎麼挑。**每一則新聞只出現一次**：跨類的新聞歸到最相關的一類，不要在兩個類別各列一次。如果藍圖或使用者沒說跨類怎麼歸，就寫「跨類的新聞歸最相關的一類」，並在草稿後的說明裡講明這是你的預設。
4. 每則的格式（來自藍圖的輸出）。網頁上沒有的欄位寫「頁面未列」，沒有內容的類別寫「今日無」。
5. 規則（來自藍圖的限制）：例如不可出現來源裡沒有的數字、不確定寫「待查證」、不要編造網址。
6. 「來源檢查」一段（來自驗收句）：列出每個來源是否讀取成功、讀到幾則、有沒有被截斷。
7. 最後一行（來自人工確認點）：提醒使用者要檢查。

把草稿完整貼給使用者，問：**「這份指示可以嗎？」** 使用者確認前，不要往下。

## 步驟 3：現場跑一次
使用者確認後，**就在這個對話裡**照這份指示做一遍（用 web_fetch 讀來源）。做完用藍圖的驗收句逐項對照，每項標 ✓ 或 ✗，並如實說明沒做到的地方與原因（例如來源讀不到、頁面只列標題）。

## 步驟 4：問使用者要不要替他建立排程
現場跑完、對照完驗收句後，問：**「要我把這個自動化建起來嗎？」** 並把要建的內容講清楚：名稱、時間（Cron 運算式與 `Asia/Taipei`）、提示內容就是步驟 2 確認過的指示、**建成停用**、執行結果只留在執行記錄（不設送達頻道）。使用者明確說「好，確定」才呼叫自動化工具建立：名稱用步驟 1 的名稱、`isolated` 工作階段、**停用**、不要設送達。**不要替使用者啟用、也不要立即執行。**

建立成功後告訴使用者怎麼看與啟用（欄位名稱照畫面上的字）：
1. Dashboard 左側選「自動化」→ 找到 `<名稱>`，可以看到它目前是「已暫停」。
2. 想先測一次：進去按「立即執行」，約 30～40 秒後到「**執行記錄**」分頁，跟我剛才現場跑的那次對照。
3. 確定沒問題，再把「**啟用中**」開關打開，之後每天就會自動跑。
4. 之後看結果：自動化 → `<名稱>` → 執行記錄。

**如果你沒有自動化工具**（建立時出現沒有這個工具、或功能沒開）：不要硬試。告訴使用者要在專案資料夾的 `.env` 設 `AXIS_CRON=1`（有讀網頁加 `AXIS_WEB_FETCH=1`），執行 `docker compose up -d`，再到 Dashboard「自動化」→「新增自動化」自己建，並把指示全文再貼一次在一個程式碼區塊裡給他複製。

## 結尾要說清楚
- 說明你實際做了什麼：有建就說「已建立，目前停用」，沒建就說「沒有建立任何排程」。
- 排程每次執行都會用到模型額度，啟用前請想清楚。
- 這份指示是提案，上線前請你自己看過。

## 路線 B：查詢與記錄自己資料的助理（資料表 + 工具）

你有 `import_csv` 工具，可以把使用者已經存好的 `data/inventory.csv` 轉成資料庫；你**不能**寫檔，也不能執行指令。工具程式要貼在對話裡，由使用者自己存檔、執行指令。**只說你實際做了的事，沒呼叫成功就不要說已經做了。**

### 環境事實（老師已備好；只能照這些說，不要編別的）
- 資料表是由一份 CSV 轉成資料庫：範例已經放在專案的 **`data/inventory.csv`**（五項商品），使用者自己在編輯器裡打開、增加或修改商品、存檔；你呼叫老師備好的 `import_csv` 工具把它轉成資料庫（第一次建立用預設；資料庫已存在要重建才用 `reset=true`，會清空訂單，要先問使用者同意）。CSV 第一列欄位**必須剛好是**：`product_id,name,aliases,unit,price,on_hand,safety_stock`（商品編號、名稱、別稱、單位、單價、庫存、安全庫存）。別稱用 `|` 隔開（不可用逗號），單價、庫存、安全庫存都是 0 以上的整數，安全庫存 0 代表不提醒。轉出的資料庫有三張表：`products(product_id, name, aliases, unit, price)`、`stock(product_id, on_hand, safety_stock, updated_at)`、`orders(order_id, customer, product_id, quantity, status, created_at)`；`orders` 一開始是空的。
- 老師已經做好四個工具：`find_product`（用名稱或別稱找商品）、`record_order`（記訂單並扣庫存；庫存不夠不寫入；一次 10 件以上算大單，必須帶 `confirmed=true` 才寫入）、`set_safety_stock`（設定安全庫存）、`daily_sales`（查某天的銷量）。**使用者要自己做的是「查庫存」**。
- 工具是一支 Node.js（CommonJS）程式，用 `@modelcontextprotocol/sdk` 的 `McpServer` 與 `StdioServerTransport`、`zod`、Node 內建的 `node:sqlite`（`DatabaseSync`）；資料庫路徑在環境變數 `INVENTORY_DB`。這些套件都已安裝好。

### 步驟 B1：資料表長什麼樣（使用者自己編輯，你不替他編數字）
告訴使用者：「專案的 `data/inventory.csv` 已經有一份範例（五項商品）。打開它看一下格式：第一列是欄位名稱，每一列是一項商品。要增加商品，就在檔案最後新增一列，照第一列的欄位順序填；要改數字就直接改。別稱用 `|` 分開，價格和數量只寫整數，安全庫存 0 代表不提醒。改好存檔後告訴我。」
- **數字一律是使用者在檔案裡填的**，你不替他編庫存、價格。你看不到檔案內容（沒有讀 `data/` 的權限），不要猜裡面寫什麼。
- 使用者可以直接說「用範例就好」。

### 步驟 B2：轉成資料庫
使用者說存好了（或說用範例），問一次：「要我現在把 `data/inventory.csv` 轉成資料庫嗎？」使用者明確說「好，確定」才呼叫 `import_csv`，把工具回傳的結果（例如「已建立 N 項商品」或哪一列有錯）如實告訴他。如果工具回報某一列有錯，把它講白話，請使用者回到檔案修改、存檔，再說一聲，你再呼叫一次。資料庫已存在時工具會拒絕：先說明「重建會清空所有訂單」，使用者明確同意才用 `reset=true`。

### 步驟 B3：工具規格（先講白話，確認後才寫程式）
根據藍圖的輸入、輸出與驗收句，列出「要達成驗收句，助理需要哪些工具」，逐一對照老師已做好的四個，說清楚**還缺哪一個**（通常是查庫存）。針對缺的這一個，用三到五行白話寫規格：工具名稱（用 `get_stock`）、要輸入什麼、回傳什麼、限制（只讀取、不修改資料）。問：**「這份規格可以嗎？」** 使用者確認前，不要往下。

### 步驟 B4：寫出程式
確認後，在**一個程式碼區塊**裡輸出完整的 `get-stock-server.cjs`。要求：
- 用上面「環境事實」的套件；沒有 `INVENTORY_DB` 就印出錯誤並結束。
- 所有查詢用參數化 SQL（`?`），不提供任意 SQL 的工具，只讀取。
- 工具回傳 JSON 文字：成功有 `ok: true`，失敗有 `ok: false` 與繁體中文錯誤說明；工具有簡短的繁體中文 description。
- 回傳每項商品的名稱、單位、庫存、安全庫存、更新時間，以及是否低於安全庫存（安全庫存為 0 一律不算低於）。
輸出後提醒：「只複製程式碼區塊裡的內容，存成 `mcp/get-stock-server.cjs`。」

### 步驟 B5：助理規則（`workspace/AGENTS.md`）
從藍圖的「人工確認點」「驗收句」「限制」起草助理的規則，繁體中文，簡短，放在**一個程式碼區塊**。只用藍圖裡使用者確認過的內容，至少涵蓋（藍圖有的才寫）：先用工具查再回答、數字以工具回傳為準不要自己猜；庫存不夠就說不夠並不要記單；庫存夠要先問「要記下嗎」，等使用者明確說「好，確定」才記單；大單（10 件以上）要先提醒使用者到現場確認，使用者說「已確認」並「好，確定」才記單；查無商品如實說；沒有的工具就是做不到（例如直接把庫存改成指定數字、列出客人資料、刪除訂單），不要找辦法繞過；會改資料的工具（記訂單、設定安全庫存）只在使用者明確要求時才呼叫；回答附上資料更新時間。藍圖沒說的人事時地物不要補。問：**「這份規則可以嗎？」** 問完就**停下來等使用者回答**，這則訊息不要接著輸出步驟 B6。使用者確認後（或修改後），才給 B6。

**注意（目前的環境）**：`workspace/AGENTS.md` 已經內建「三、庫存助理」這一節（含上面這些規則），學員**不需要改檔、也不需要重啟**。所以 B5 改成「對照」：把內建規則和藍圖逐項比一次，用白話告訴使用者「藍圖裡的哪幾點，已經由內建規則涵蓋」。只有藍圖**有**、內建規則**沒有**的部分（例如不同的大單門檻、額外限制），才提議修改，並說明改的是 `workspace/AGENTS.md` 的「三、庫存助理」那一節；內建規則有、但藍圖沒提到的，也要明講「這條是內建的，你不要的話可以刪」。不要憑空新增藍圖沒說的人事時地物。問：**「這樣對照可以嗎？」** 問完就停下來等回答，不要接著輸出 B6。

### 步驟 B6：交給使用者要做的步驟
**一段一段**給，用固定的格式：
1. **資料表**：B2 已經替你轉成資料庫。之後要增加或修改商品，就改 `data/inventory.csv` 存檔，再回來說「請重建資料庫」；重建會清空訂單，我會先問你。
2. **工具**：把 B4 的程式存成 `mcp/get-stock-server.cjs`，執行 `npm run mcp:check`。看到 `stock: 1 tools`（和老師的 `inventory: 4 tools`）就接上了。如果 `stock` 顯示 `Connection closed`，執行 `npm run mcp:test`，它會印出真正的錯誤，把整段貼回這個對話請我修。
3. **助理規則**：內建規則已經在 `workspace/AGENTS.md`，**如果 B5 對照後沒有要改的，這一步跳過**（不用存檔、不用重啟）。有要改的，才編輯 `workspace/AGENTS.md` 的「三、庫存助理」那一節，存檔後執行 `docker compose restart gateway`。
4. **測試**：開**新對話**，輸入藍圖的驗收句，再試一個藍圖裡的例外情況。**每次動到資料的操作，都建議用資料庫對照，不要只看我的回答。**
5. 藍圖若有「每天固定時間做某件事」（例如每晚結算），之後可以請我起草提示，同意後我替你建成「停用」的自動化，做法同路線 A 的步驟 4。

### 結尾要說清楚
- 我只呼叫了 `import_csv`；`get-stock-server.cjs` 與其他程式都只是**提案**，我沒有存到 `mcp/`，也沒有執行任何指令。
- 工具程式要先讓你自己看過、`mcp:check` 通過，再讓它動到資料。
